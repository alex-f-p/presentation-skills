# Design presentation slides

Turn a brief, storyboard or existing deck into slides the audience can use. When the request is only for design advice or wording, give that and stop.

## Read first

- [Editorial rules](references/editorial-rules.md), always.
- [Visual representations](references/visual-representations.md) for charts, tables, diagrams, screenshots, quotations and imagery.
- [Composition and reveals](references/composition-and-reveals.md) for titles, layout and content revealed in steps.
- [Production and access](references/production-and-access.md) for building slides, accessible media or exports.

## Steps

1. Fix the content first. Deal with unsupported claims and missing prerequisites before working on appearance, and improve the storyboard where it helps.
2. Choose each representation for what the audience must do with it. Keep every claim with its evidence and qualifications, and keep the comparisons, labels and context the audience needs.
3. Build with the authoring tools available for the requested format. Check the tool’s default styling against the brief and the editorial rules before accepting it.
4. If the visual approach is unproven, render one representative content slide and inspect it before building the rest. Fix what is wrong first. Compare alternative designs only to settle a specific doubt.
5. Render the slides you made or changed, their reveal states and the requested exports. Inspect them at the size the audience will see: small essential labels, clipping, missing assets and font rendering.
6. Check every slide you made or changed against the editorial rules.
7. Repair, re-render and recheck until the affected slides pass.
8. Read any reading version with no narration, and confirm recipients can open its notes.

## Rules

- Keep the requested scope, format, template, slide count and editability. A deck supplied as source content is a template only if the user says so.
- Keep a small repair small. Change what was asked and what that breaks, and note any change that affects earlier decisions.
- Report only the checks you performed, and name their limits. An output you could not render and inspect is an unverified draft; say so.
- Never describe source code alone as ready to present.

## Output

Deliver the deck or its location, the exports and any supporting material the request needs. For text-only advice, return the advice and name the visual checks nobody has performed. Chat-only requests stay in chat, and a small repair needs no record.

For a saved project, write to its working document, or to `presentation.md` beside the presentation files. Read the existing sections first. Update `Outputs` with links to the source, notes and exports, and state what was checked and on which revision. Update earlier decisions or claims that a repair changed. See the [output example](references/output-example.md) for structure. End with a continuation note: remaining work, and outputs that need rechecking.
