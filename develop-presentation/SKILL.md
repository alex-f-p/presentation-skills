# Develop a presentation

Build the argument, outline or storyboard the request asks for, at the depth it asks for.

## Read first

- [Editorial rules](references/editorial-rules.md) before writing any wording the audience will see.
- [Argument and evidence](references/argument-and-evidence.md) for claims, recommendations or source conflicts.
- [Storyboard and channels](references/storyboard-and-channels.md) for sequencing, or for adapting between live and reading use.
- [Technical explanation and demos](references/technical-explanation-and-demos.md) for unfamiliar measures, mechanisms or demonstrations.

## Steps

1. Start from the supplied brief, outline or deck. Keep what is sound and resolve only the gaps that would change the argument.
2. Follow the evidence. If it does not support the intended conclusion, change the conclusion.
3. Order the audience’s questions and prerequisites so each step follows from the last. Choose examples, activities and transitions that move toward the outcome.
4. Divide the content into scenes. A scene is one audience task. It may take several slides or reveal states, and a comparison may need several objects on screen together.
5. Write to the depth requested. An outline gives the purpose of each section, in order. A storyboard gives the fields below for each scene.
6. Check the logic as plain text, before any layout can flatter it. Verify claims and calculations, define the terms the audience needs, and estimate time for reading, interaction and recovering from problems.
7. Check every title and takeaway against the editorial rules.
8. If the audience or achievable outcome has changed, update the brief.

| Scene field | Contents |
| --- | --- |
| Audience task | What the audience does with this scene. |
| Takeaway or question | The point, in one sentence. |
| Evidence | Source, values and qualifications. |
| Visible | What is on screen. |
| Spoken | What the speaker adds. |
| Reference | What goes in supporting material. |
| Transition | Why the next scene follows. |
| Check | A question that shows whether the audience got it. |

## Rules

- Keep each qualification that changes a claim’s meaning on screen with the claim, not only in notes.
- Keep together what the audience must compare, such as alternatives shown side by side.
- Label every estimate as an estimate.
- Stop at the requested depth. Go on to slides only if the request includes them, and never pause for approval between stages.

## Output

Return the outline or storyboard and the open questions that affect it. Chat-only requests stay in chat, and a small advice request needs no file.

For a saved project, write to its working document, or to `presentation.md` beside the presentation files. Read the existing sections first, update `Content` and keep settled decisions. Put sources and qualifications beside their claims. See the [output example](references/output-example.md) for an outline and a scene. End with a continuation note: what remains within the request, and which earlier decisions or later outputs now need updating.
